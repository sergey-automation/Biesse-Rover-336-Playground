# SIR88 RP2040 v0.1 — устройство программ и форматы данных

Основание: исходники `SIR88_RP2040_firmware_v0.1.zip`, ТЗ v1.1. Описание относится к существующей версии, код не изменён.

## 1. Состав проекта

| Файл | Назначение |
|---|---|
| `sir88.py` | Управляющий скрипт ПК: загрузка Command, настройки, запуск, декодирование и сохранение RS |
| `main.c` | Автономное исполнение пакета, управление DE и /RE, таймеры, буферы, XOR, ACK/RET/NAK, USB-протокол |
| `uart9.pio` | Две машины PIO: передача и приём UART 9N1 |
| `usb_descriptors.c` | USB-дескрипторы |
| `tusb_config.h` | Настройки TinyUSB |
| `CMakeLists.txt` | Сборка Pico SDK |
| `TZ.md` | Техническое задание v1.1 |
| `README.md` | Инструкция по сборке и запуску |

Термины: Command — команда, RS — ответ, Frame — кадр. Одна Command или один RS занимает один Frame на RS-485. USB использует отдельный формат сообщений.

## 2. Поток данных

```text
Командная строка --cmd  ИЛИ  JSON-файл --file
                    ↓
               sir88.py
                    ↓ USB CDC: LOAD, START
            RP2040: RAM, main.c, PIO
                    ↕ RS-485 750000 бод, 9N1
                  SIR88
                    ↑
            RP2040: накопление RS
                    ↓ USB CDC: RESULTS
               sir88.py
                    ↓
           Консоль + JSON результатов
```

Python читает команды из одного источника (совместное использование `--cmd` и `--file` запрещено). Он не читает напрямую RS-485 и не рассчитывает временные интервалы физической передачи. После LOAD и START прошивка исполняет пакет самостоятельно. Прикладные USB-команды обрабатываются между пакетами. USB обслуживается также между отдельными обменами. Результаты выгружаются после завершения пакета. Flash при опросе не записывается.

GPIO: GP0 DI, GP1 DE, GP2 /RE, GP3 RO, GP25 LED. Частота ядра 120 МГц. PIO делитель 10, 16 циклов PIO на бит передачи. 1 бит = 1,333333 мкс; 1 слово 9N1 = 11 бит = 14,666667 мкс.

## 3. Входные данные Python

### 3.1. Из командной строки

```cmd
python sir88.py --port COM18 --cmd 130 0BA 1BC 136 --expected 3 --xor 100
```

Слова после `--cmd` и значение `--xor` читаются как шестнадцатеричные числа. `--expected` — десятичное число. Несколько Command задаются повторением `--cmd`.

### 3.2. Из JSON-файла

```json
[
  {"tx": [304, 186, 444, 310], "expected": 3, "xor": 256},
  {"tx": [307, 8, 269, 310], "expected": 3, "xor": 256}
]
```

Первая запись: `130 0BA 1BC 136`. Вторая: `133 008 10D 136`. Обе ранее передавались на стенде.

| Поле | Тип | Ограничение |
|---|---|---|
| `tx` | Массив целых чисел | 1–7 слов, каждое 0–511 (000–1FF hex) |
| `expected` | Целое число | 1–6, минимальное ожидаемое число слов RS |
| `xor` | Целое число | 0–511, ожидаемый XOR |

В файле JSON числа записываются десятичными, без кавычек и без префикса `0x`. Корневой элемент — массив из 1–512 записей. Для `--file` поля `expected` и `xor` берутся из каждой записи, а не из глобальных аргументов `--expected` и `--xor`. Повторяющиеся записи допустимы. Иные поля не используются скриптом.

Создание 20 одинаковых Command:

```cmd
python -c "import json; json.dump([{'tx':[0x130,0x0BA,0x1BC,0x136],'expected':3,'xor':256}]*20,open('test20.json','w'))"
```

В этой команде шестнадцатеричные литералы принадлежат языку Python; `json.dump` преобразует их в десятичные числа JSON.

```cmd
python sir88.py --port COM18 --file test20.json --auto 0 --ret 0 --period-us 352
```

## 4. Параметры запуска

| Аргумент | По умолчанию | Назначение |
|---|---:|---|
| `--port` | — | COM-порт USB CDC |
| `--list` | — | Список COM-портов |
| `--self-test` | — | Проверка кодирования, CRC и декодирования без платы |
| `--cmd` | — | Command в hex, можно повторять |
| `--file` | — | Входной JSON |
| `--expected` | 3 | Минимальная длина RS при --cmd |
| `--xor` | 100 hex | Ожидаемый XOR при --cmd |
| `--auto` | 0 | 0 — без подтверждений; 1 — автоматические подтверждения |
| `--ret` | 0 | Максимум RET, от 0 до 5 |
| `--start-us` | 73,333333 | Ожидание начала первого RS, мкс |
| `--gap-us` | 13,2 | Межсловный тайм-аут, мкс |
| `--period-us` | 352 | Минимальный период между началами Command, мкс |
| `--ret-us` | 73,333333 | Ожидание начала RS после RET, мкс |
| `--confirm-us` | 0 | Дополнительная задержка подтверждения, мкс |
| `--timeout` | 30 | Тайм-аут USB в секундах, не RS-485 |
| `--output` | sir88_results.json | Выходной JSON |
| `--repeat` | 1 | Число исполнений загруженного пакета |

Python переводит микросекунды в такты: `int(us*120+0.5)`. Диапазон start/gap/ret: 1–65535 тактов; confirm: 0–65535; period: 38720–4294967295. Минимум периода 322,667 мкс. При длинном обмене период увеличивается: пересечения обменов нет. Порт открывается с параметром 115200 для USB CDC; скорость физической линии RS-485 определяется PIO независимо.

## 5. Выходной JSON

Пример структуры на основе зарегистрированного RS `130 004 034` с задержкой 25,683333 мкс. Это иллюстрация формата, не копия конкретного файла результатов.

```json
[
  {
    "status": 0,
    "commands": [
      {
        "tx": [304, 186, 444, 310],
        "expected": 3,
        "expected_xor": 256,
        "attempts": [
          {
            "attempt": 0,
            "rx": [304, 4, 52],
            "count": 3,
            "error_mask": 0,
            "confirm": 0,
            "xor": 256,
            "delay_ticks": 3082,
            "delay_us": 25.683333333333334
          }
        ]
      }
    ]
  }
]
```

| Поле | Значение |
|---|---|
| `status` | Статус пакета; текущая прошивка формирует 0 при выгрузке |
| `commands` | Список выполненных Command в порядке исполнения |
| `tx` | Фактически возвращённые прошивкой слова Command |
| `expected` | Минимальная длина RS |
| `expected_xor` | Ожидаемый XOR из входного поля `xor` |
| `attempts` | Только слоты RS с valid=1 |
| `attempt` | 0 — исходный RS; 1–5 — окна после RET |
| `rx` | Первые min(count,6) слов RS |
| `count` | Полное число принятых слов, максимум 255 |
| `error_mask` | Бит i = ошибка стопового бита слова i (первые 6 слов, нумерация с 0) |
| `confirm` | 0 — нет; 1 — ACK; 2 — RET; 3 — NAK |
| `xor` | XOR первых максимум шести слов, учитываются все 9 бит |
| `delay_ticks` | Программно измеренная задержка начала RS, в тактах 120 МГц |
| `delay_us` | delay_ticks / 120; null при отсутствии слов |

TIMEOUT представлен как `rx: []`, `count: 0`, `delay_us: null`. Неиспользованные слоты не экспортируются. Выходной файл содержит массив исполнений пакета. При `--repeat 3` в нём до трёх объектов пакетов. В каждом запуске скрипта файл перезаписывается, а не дополняется результатами предыдущих запусков. Внутри одного запуска после каждого исполнения сохраняется накопленный массив. Настройки таймингов не включаются в выходной JSON автоматически.

Консоль выводит слова и XOR в hex, N в десятичной форме, ERR в hex, задержку в мкс. Например:

```text
TX 130 0BA 1BC 136
 RX 130 004 034 N=3 ERR=00 XOR=100 DELAY=25.683333333333334 us CONF=0
```

## 6. Бинарный USB-протокол

Формат сообщения: MAGIC (2 байта A5 5A), opcode (1), длина payload (4, LE), payload, CRC32 (4, LE). LE — младший байт первым. CRC-32/ISO-HDLC считается по opcode + длине + payload, без MAGIC. Накладные расходы 11 байт.

| Opcode hex | Назначение |
|---|---|
| 01 | LOAD: загрузка настроек и Command |
| 02 | START: первый запуск |
| 03 | REPEAT: повтор завершённого пакета |
| 04 | STOP: между пакетами |
| 05 | GET SETTINGS |
| 06 | GET STATE |
| 81 | ACK USB, payload содержит opcode запроса |
| 82 | RESULTS |
| 85 | SETTINGS |
| 86 | STATE |
| FF | Ошибка: opcode запроса и код ошибки |

Не путать ACK USB (`81`) и ACK линии RS-485 (`000`). Скрипт CLI непосредственно использует LOAD, START, REPEAT и принимает ACK/RESULTS; отдельные CLI-команды для STOP/GET SETTINGS/GET STATE не реализованы.

### 6.1. Настройки LOAD, 24 байта (`<HBB5I`)

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 2 | Число Command |
| 2 | 1 | AUTO |
| 3 | 1 | RET_MAX |
| 4 | 4 | START ticks |
| 8 | 4 | GAP ticks |
| 12 | 4 | PERIOD ticks |
| 16 | 4 | RET_START ticks |
| 20 | 4 | CONFIRM_DELAY ticks |

Далее N записей Command по 18 байт (`<BBH7H`): длина 1 байт, expected 1 байт, XOR 2 байта, семь слов uint16 (14 байт), неиспользованные слова нулевые.

### 6.2. RESULTS

Заголовок payload 4 байта: status (1), reserved (1, ноль), число завершённых Command (2). Далее N записей по 138 байт: Command (18) и шесть слотов RS по 20 байт. Формат RS `<6H4B2H`:

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 12 | 6 слов uint16 |
| 12 | 1 | count |
| 13 | 1 | error_mask |
| 14 | 1 | confirm |
| 15 | 1 | valid |
| 16 | 2 | XOR |
| 18 | 2 | delay_ticks |

Для 512 Command: LOAD payload 9240 байт, полное USB-сообщение 9251 байт; RESULTS payload 70660 байт, полное сообщение 70671 байт. Результаты сериализуются напрямую из буферов, отдельный полный буфер RESULTS не нужен.

## 7. Автоматические подтверждения RS-485

| Условие | Действие |
|---|---|
| AUTO=0 | Нет подтверждений |
| count=255 | Нет подтверждений |
| Первый RS отсутствует | Нет подтверждений |
| Ошибка стопового бита в первых 6 словах | NAK 0FF |
| RS после RET отсутствует, RS короче expected или singleton 0AA | RET 0AA при доступном лимите, иначе NAK 0FF |
| Достаточно слов, XOR совпадает | ACK 000 |
| Достаточно слов, XOR не совпадает | NAK 0FF |

RET открывает новое окно приёма RS, а не повторяет исходную Command. Максимум 6 слотов на Command. При отсутствии RS после RET сохраняется действительный пустой слот.

## 8. RAM — расчёт по исходному коду

База: максимальный пакет 512 Command, RP2040 SRAM 264 КиБ = 270336 байт.

| Буфер | Байты | КиБ |
|---|---:|---:|
| `cmds[512]` | 9216 | 9 |
| `rs[512][6]` | 61440 | 60 |
| `payload[9240]` | 9240 | 9,023 |
| Итого три основных массива | 79896 | 78,023 |
| Остаток до остальных объектов, стеков и USB | 190440 | 185,977 |

Ранее оценка остатка 195 КиБ учитывала только Command и RS, без отдельного входного USB-буфера. Точный свободный объём RAM не измерен; нужен map-файл сборки и оценка стека.

## 9. Ограничения и состояние проверки

На стенде были выполнены пакеты до 512 одинаковых Command, в том числе с AUTO=1 и RET=5. Получение короткого RS `135` не означает отсутствия ответа; его смысл не установлен. Поведение при различных Command, длинных RS, ошибках стопового бита и точность фактических физических таймингов полностью не проверены. Программный DELAY включает задержку наблюдения PIO IRQ; GAP отсчитывается от программного наблюдения принятого слова. STOP не прерывает исполняемый пакет. Статус 0 не является признаком корректности каждого RS. Примеры в этом документе основаны на уже использованных командах стенда, без исполнительных нагрузок. Прошивка и Python не изменены.
